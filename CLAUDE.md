# Neura Dataflow Compiler — Developer Guide for Claude

## Project Overview

This repository implements a CGRA (Coarse-Grained Reconfigurable Architecture) compiler built on top of MLIR. It:
- Defines the **Neura dialect**: a predicated dataflow IR for loop bodies mapped to CGRA tiles.
- Provides compilation **passes** that lower C/C++ (via LLVM IR) to a spatially and temporally mapped Neura IR.
- Maps ops onto a mesh CGRA using a **heuristic backtracking mapper** (`map-to-accelerator`).

## Repository Layout

  Architecture/               # ArchitectureSpec parsing, Architecture/Tile/Link classes

```sh
cd dataflow
mkdir build && cd build
cmake -G Ninja .. \
  -DLLVM_DIR=/workspace/llvm-project/build/lib/cmake/llvm \
  -DMLIR_DIR=/workspace/llvm-project/build/lib/cmake/mlir \
  -DMLIR_SOURCE_DIR=/workspace/llvm-project/mlir \
  -DMLIR_BINARY_DIR=/workspace/llvm-project/build \
  -DCMAKE_CXX_FLAGS="-std=c++17"
ninja mlir-neura-opt
```

The main binary is `build/tools/mlir-neura-opt/mlir-neura-opt`.

## End-to-End Compilation Pipeline

A representative pipeline is demonstrated in `test/neura/fusion/run.sh`. The pipeline below covers the fusion-based path for a single kernel; other kernels or optimization targets may require additional passes (e.g., task-level fusion). Each intermediate file is preserved for debugging.

| Step | Pass(es) | Input → Output |
|------|----------|----------------|
| 1 | `clang++ -S -emit-llvm` | `kernel.cpp` → `kernel.ll` |
| 2 | `mlir-translate --import-llvm` | `kernel.ll` → `kernel.mlir` |
| 3 | assign-accelerator, lower-llvm-to-neura, promote-input-arg-to-const, canonicalize-\*, leverage-predicated-value, fold-constant | `kernel.mlir` → `kernel_before.mlir` |
| 4 | transform-ctrl-to-data-flow, fold-constant | `kernel_before.mlir` → `kernel_before0.mlir` |
| 5 | iter-merge-pattern | `kernel_before0.mlir` → `kernel_after0.mlir` |
| 6 | hardware-merge | `kernel_after0.mlir` → `kernel_after01.mlir` + `hardware_config.json` |
| 7 | init-exec-latency | `kernel_after01.mlir` → `kernel_after1.mlir` |
| 8 | insert-data-mov | `kernel_after1.mlir` → `kernel_after2.mlir` |
| 9 | map-to-accelerator | `kernel_after2.mlir` → `kernel_after3.mlir` |

### Configuration Files

**`latency_map.yaml`** — provides execution latency (in cycles) for each operation or fused pattern:
```yaml
gep->load: 3
phi_start->fused_op:gep->load: 4
grant_once->fused_op:phi_start->phi_start: 3
```
Single ops use their short name (e.g., `mul: 2`). Fused ops use their `pattern_name` attribute exactly as it appears in the MLIR (e.g., `fused_op:icmp->grant_predicate->grant_predicate: 3`). Both `fused_op:<pattern>` and bare `<pattern>` keys are accepted; `fused_op:` prefix takes priority. Any op not found in the map defaults to latency 1.

**`hardware_config.json`** — generated by `--hardware-merge`, describes hardware templates. Each template lists which single ops and composite ops (fused ops by `pattern_name`) it supports, and how they execute across pipeline stages. Passed to `--map-to-accelerator` via `hardware-config=hardware_config.json` to enforce template compatibility during mapping.

**`architecture.yaml`** — describes the CGRA topology. Key fields:
```yaml
per_cgra_defaults:
  rows: 4
  columns: 4    # 4×4 tile mesh
tile_defaults:
  num_registers: 32
  fu_types: [add, mul, phi, mem, ...]
```
Passed to most passes via `--architecture-spec=<path>`.

## Code Conventions

### Comments
- All comments start with `//`.
- Comment text uses third person singular (e.g., *"Parses the YAML file and populates the latency map."*).
- Every function definition requires a preceding comment describing its purpose.
- Inside function bodies, only non-obvious or critical logic needs a comment. Straightforward code is left uncommented.
- Comments are concise; no redundant restating of what the code already clearly expresses.

Example:
```cpp
// Looks up the latency for the given operation in the latency map.
// Returns 1 if the op is not found.
int getLatency(Operation *op, const std::map<std::string, int> &latency_map) {
  std::string key = op->getName().getStringRef().str();
  auto it = latency_map.find(key);
  if (it != latency_map.end())
    return it->second;
  return 1;
}
```

### Variable Naming
All variables, parameters, and local names use **snake_case**:
```cpp
int time_step = 0;
std::string pattern_name = fused_op.getPatternName().str();
std::map<std::string, int> latency_map;
```

### Line Breaks
- A statement that fits on one line must not be split across multiple lines. This applies to return statements, ternary initializations, and any other expression that reads naturally as a single line.
- `llvm::errs()` output chains should be compact: group all fields for one logical item on the same continuation line rather than one field per line.

Example:
```cpp
// Bad
return static_cast<int>(
    std::ceil(factor * mii));
int x = condition ? value_a
                  : value_b;
llvm::errs() << "rec=" << rec_mii
             << " res=" << res_mii
             << " ops=" << num_ops << "\n";

// Good
return static_cast<int>(std::ceil(factor * mii));
int x = condition ? value_a : value_b;
llvm::errs() << "rec=" << rec_mii << " res=" << res_mii << " ops=" << num_ops << "\n";
```

### Shell / Bash Scripts
- No comments inside scripts.
- No intermediate `echo` output statements.
- Use `set -e` at the top.

Example:
```bash
#!/bin/bash
set -e
mlir-neura-opt --init-exec-latency --latency-spec=latency_map.yaml input.mlir -o output.mlir
```
